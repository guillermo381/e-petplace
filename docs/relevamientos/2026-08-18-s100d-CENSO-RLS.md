## 🔴 ③ `consentimientos` — **NO APLICADA. La firma era condicional y la condición FALLÓ**

La firma decía: *«Censá antes en las webs del legado si algún flujo inserta CON
`user_id`; si ninguno, aplicá»*. **Censado: hay uno, y aplicar rompería el
registro.**

**El único escritor real en los siete repos** (excluyendo `dist/` y tipos
generados) — `e-petplace-v2/src/pages/Login.tsx:328`:

```js
const { data, error: err } = await supabase.auth.signUp({ email, password, … });
…
await supabase.from('consentimientos').insert({
  user_id: data.user.id, tipo: 'registro', aceptado: true,
});
…
if (data.session) { history.replace('/onboarding'); }
else { setSuccess('¡Cuenta creada! Revisa tu email para confirmar tu acceso.'); }
```

**Inserta CON `user_id`. Y las tres líneas de abajo son las que deciden:** cuando
el proyecto exige confirmar el correo, **`data.session` es null ⇒ el cliente
sigue siendo `anon` ⇒ `auth.uid()` es NULL**.

⇒ con `WITH CHECK (user_id IS NULL OR user_id = auth.uid())`:
`user_id` **no** es NULL y `auth.uid()` **sí** ⇒ **el CHECK rechaza y el alta
falla**. *La cura de una línea es correcta como idea y falsa como parche: el
flujo legítimo y la forja son **indistinguibles en la base**, porque los dos son
«anon escribiendo un `user_id` ajeno».*

**⚠️ Y no alcanza con que el flujo parezca dormido:** las 59 filas son del
25-abr al 10-may-2026 y no hay ninguna nueva, pero *dormido no es muerto* — y el
modo de falla es el alta de un usuario real.

**LA CURA QUE SÍ CIERRA, y es estructural, no de una línea:** el consentimiento
tiene que dejar de ser **un dato que el cliente afirma** y pasar a ser **una
consecuencia del registro** — una `SECURITY DEFINER` llamada en el alta, o un
trigger sobre la creación de la cuenta. *Volver el estado malo inexpresable en
vez de vigilarlo* (L-222). **Pide su propia decisión y su propio turno: toca el
alta de una web viva que no es de este monorepo.**
